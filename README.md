# Fire Safety — Система управления инцидентами пожарной безопасности

## Стек

- **Frontend**: React 18, Vite, React Router v6, Axios
- **Backend**: Node.js 20, Express 4, PostgreSQL 15
- **Инфраструктура**: Docker, docker-compose, GitHub Actions

## Быстрый старт

1. Скопируйте файл переменных окружения:
   cp .env.example .env

2. Откройте `.env` и замените все значения `CHANGE_ME` на реальные секреты.

3. Запустите все сервисы:
   docker-compose up --build

4. Откройте в браузере:
   - Приложение: http://localhost
   - API-документация (Swagger): http://localhost:3000/api-docs
   - pgAdmin: http://localhost:5050 (admin@admin.com / admin)

## Резервное копирование

Ручной дамп базы данных выполняется командой:

docker exec -t $(docker ps -qf "name=db") pg_dump -U admin fire_safety_laba4 > backup_$(date +%Y%m%d_%H%M%S).sql



Рекомендуется добавить эту команду в cron для регулярного автоматического бэкапа, например ежедневно в 3:00 ночи:

0 3 * * * docker exec -t $(docker ps -qf "name=db") pg_dump -U admin fire_safety_laba4 > /backups/fire_safety_$(date +\%Y\%m\%d).sql



Хранить дампы рекомендуется вне контейнера (на отдельном диске или в облачном хранилище), с ротацией старых файлов (например, хранить последние 14 дней).

## Восстановление после сбоя

Восстановление БД из дампа выполняется командой:

cat backup_20260101_030000.sql | docker exec -i $(docker ps -qf "name=db") psql -U admin -d fire_safety_laba4



Перед восстановлением рекомендуется остановить сервис `api`, чтобы избежать конфликтов при записи:

docker-compose stop api



После восстановления БД снова запустить сервис:

docker-compose start api



## Мониторинг

- Все ошибки уровня `error` пишутся в файл `server/logs/error.log` (формат JSON, ротация не настроена — рекомендуется добавить `winston-daily-rotate-file` при росте нагрузки).
- Информационные логи выводятся в консоль контейнера `api` (`docker-compose logs -f api`).
- Аудит действий пользователей (входы, ошибки авторизации, создание/изменение/удаление записей, отказ в доступе) фиксируется в таблице `audit_logs` и доступен только администратору через прямой запрос к БД (эндпоинт просмотра журнала можно добавить отдельно).
- Для оповещений о критических ошибках рекомендуется настроить дополнительный `winston` transport на email или Telegram, например:


const nodemailerTransport = require('nodemailer');


Такой transport не входит в текущую реализацию, но может быть подключён без изменения остальной логики логирования.
Порядок обновления приложения

Обновление до новой версии выполняется следующими командами:


git pull origin main
docker-compose pull
docker-compose up -d --build

Перед обновлением рекомендуется сделать резервную копию БД (см. раздел «Резервное копирование»). Миграции применяются автоматически при первом создании контейнера db (том pgdata); при обновлении схемы БД на уже существующей базе новые файлы миграций нужно применять вручную через psql или docker exec.
Масштабирование

    Backend: приложение не хранит состояние в памяти процесса (сессии — в БД/JWT), поэтому можно запускать несколько реплик api за балансировщиком нагрузки (например, nginx или облачный LB).

    База данных: при росте нагрузки рекомендуется вынести PostgreSQL на отдельный управляемый сервис (RDS, Cloud SQL) с репликами для чтения.

    Frontend: статические файлы React-приложения можно раздавать через CDN.

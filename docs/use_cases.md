# Пользовательские сценарии

## Роли системы
- **admin** — полный доступ ко всем разделам, включая управление пользователями, удаление любых записей, а также создание, изменение и удаление датчиков.  
- **dispatcher** — создание и частичное редактирование инцидентов и зданий (ограниченный набор полей), без доступа к управлению пользователями и без права удаления. Может просматривать датчики, но не управлять ими.  
- **user** — только просмотр инцидентов, зданий, датчиков и карты. Не имеет прав на создание, изменение или удаление каких-либо сущностей.

---

## Сценарий 1: Вход в систему
- **Кто выполняет:** любой зарегистрированный пользователь.  
- **Проверяемые данные:** email, пароль (хеш через bcrypt).  
- **Что логируется:** `LOGIN_SUCCESS` или `LOGIN_FAILED` в `audit_logs` с IP и user-agent.  
- **При ошибке:** общее сообщение «Неверный email или пароль» без указания, какой параметр неверен. После 3 неудачных попыток за 10 минут — блокировка IP на 10 минут (HTTP 429), логируется `LOGIN_BLOCKED`.  
- **Запрещено:** подбор пароля методом перебора (защищено брутфорс-лимитом); использование чужого refresh-токена (при повторном логине все старые refresh-токены пользователя отзываются).

---

## Сценарий 2: Просмотр списка инцидентов
- **Кто выполняет:** admin, dispatcher, user.  
- **Проверяемые данные:** JWT access-токен в заголовке `Authorization: Bearer`.  
- **Что логируется:** неудачные попытки доступа без токена (`AUTH_FAILED`).  
- **При ошибке:** HTTP 401 при отсутствии/невалидном токене; HTTP 422 при некорректных параметрах фильтрации.  
- **Запрещено:** доступ без аутентификации.

---

## Сценарий 3: Создание инцидента
- **Кто выполняет:** admin, dispatcher.  
- **Проверяемые данные:** адрес, дом, этаж (целое ≥ 1), тип угрозы, уровень угрозы, статус, ответственный — валидируются через Joi. Опционально: квартира, описание.  
- **Что логируется:** `CREATE_INCIDENT` в `audit_logs`, запись в `incidentlogs`.  
- **При ошибке:** HTTP 422 при невалидных данных, HTTP 403 при недостаточных правах.  
- **Запрещено:** создание инцидента пользователем с ролью user.

---

## Сценарий 4: Изменение инцидента
- **Кто выполняет:** admin (все поля), dispatcher (только статус).  
- **Проверяемые данные:** те же поля, что при создании, все опциональны при обновлении.  
- **Что логируется:** `UPDATE_INCIDENT`, запись в `incidentlogs`.  
- **При ошибке:** HTTP 404, если инцидент не найден; HTTP 403, если роль не позволяет редактировать; HTTP 422 при пустом/невалидном теле запроса.  
- **Запрещено:** изменение любых полей, кроме статуса, диспетчером; любые изменения пользователем.

---

## Сценарий 5: Удаление инцидента/здания/датчика
- **Кто выполняет:** только admin.  
- **Проверяемые данные:** существование записи в БД.  
- **Что логируется:** `DELETE_INCIDENT` / `DELETE_BUILDING` / `DELETE_SENSOR`.  
- **При ошибке:** HTTP 404, если запись не найдена; HTTP 403, если роль не admin.  
- **Запрещено:** удаление любой сущности ролями dispatcher и user.

---

## Сценарий 6: Управление пользователями
- **Кто выполняет:** только admin.  
- **Проверяемые данные:** id пользователя, новая роль (`admin`/`dispatcher`/`user`).  
- **Что логируется:** `UPDATE_USER_ROLE`, `DELETE_USER`.  
- **При ошибке:** HTTP 403 при попытке удалить самого себя; HTTP 404, если пользователь не найден; HTTP 422 при недопустимой роли.  
- **Запрещено:** просмотр и изменение пользователей ролями dispatcher и user; удаление собственной учётной записи.

---

## Сценарий 7: Экспорт данных в CSV
- **Кто выполняет:** admin, dispatcher, user (любой аутентифицированный).  
- **Проверяемые данные:** параметры фильтрации/поиска, формат (только `csv`). Доступны два эндпоинта:  
  - `/incidents/export` — экспорт инцидентов с учётом фильтров по статусу, серьёзности и поисковому запросу.  
  - `/buildings/export` — экспорт зданий с учётом фильтра поиска по названию, адресу и номеру дома.  
- **Что логируется:** `EXPORT_INCIDENTS_CSV` / `EXPORT_BUILDINGS_CSV` с количеством выгруженных записей.  
- **При ошибке:** HTTP 401 без токена; HTTP 422 при неверном формате.  
- **Запрещено:** экспорт без аутентификации.

---

## Сценарий 8: Управление датчиками
- **Кто выполняет:**  
  - **Просмотр списка датчиков** — admin, dispatcher, user (все аутентифицированные).  
  - **Создание, изменение, удаление датчиков** — только admin.  
- **Проверяемые данные:** при создании — `building_id` (существующее здание), `type` (строка), `location` (опционально), `status` (active/inactive/maintenance). При обновлении — опциональные поля.  
- **Что логируется:** `CREATE_SENSOR`, `UPDATE_SENSOR`, `DELETE_SENSOR` в `audit_logs`.  
- **При ошибке:** HTTP 422 при невалидных данных; HTTP 403 при недостаточных правах; HTTP 404 при попытке сослаться на несуществующее здание или датчик.  
- **Запрещено:** создание/изменение/удаление датчиков пользователями с ролями dispatcher и user.

---

## Сценарий 9: Просмотр карты инцидентов
- **Кто выполняет:** admin, dispatcher, user (все аутентифицированные).  
- **Проверяемые данные:** JWT токен, наличие у инцидентов координат (latitude/longitude).  
- **Что логируется:** не логируется отдельно (только общие ошибки доступа).  
- **При ошибке:** HTTP 401 при отсутствии токена.  
- **Запрещено:** просмотр карты без аутентификации.
